## W1 — Format 2

- `apps/cockpit/cockpit/workspace_registry.py` (standard library only): `instances()` reads format 2 and gives every
  instance in the shape of a format-1 entry, plus its workspace and its seed. The cockpit (`workspaces.py`), the runner
  (`queues`, mailboxes) and pressroom-env all read through it — pressroom-env loads the module from the stage's checkout.
- A connector has a kind, a root and, where writes go another way (a WebDAV mount), a write root. A data point is a
  place on a connector, with readers, writers and an optional seed. An instance binds `cases` to one data point, or to
  several plus a `home`; it may narrow the workspace's members.
- A workspace that is `open` lets every signed-in person in; otherwise its members only. In format 1 every shared entry
  was open to everybody signed in; after the move, an instance such as a personal inbox is closed to the others.
- Format 2 saves back as format 2; a new instance gets a data point of its own on the server's directory connector.
- `/w/<instance>/` is unchanged: links, tokens and sessions keep their addresses.
- In format 2 pressroom-env no longer seeds workspaces; it still writes the inboxes' targets (ADR-022).

## W2 — Migration

- `cockpit workspace migrate --plan plan.json [--write]`: the plan names the connectors and, per workspace, its
  instances; every format-1 entry exactly once. Applications over the same configuration become one (the shortest id
  stays); the others were samples filed as applications, and their template becomes the seed of the instance's data point.
- `check()` compares every instance before and after — root, write root, mode, application, configuration, template,
  person picker, data points. Anything different and nothing is written. With `--write` the old file stays beside it
  (`.format1`).

## W3 — The rail

- `PlaceOut` carries `workspace` and `workspace_label`; the rail shows one group per workspace, the one you are in
  open, the others folded until opened. Without workspaces (format 1, the public demo) it looks as before.

## W4 — Creating

- `/workspaces/new` in format 2: first "new workspace" (id, name, open or not; the creator is its first member), then
  "add an application to a workspace" (the workspace, the application, id, name, start from). CLI: `--in <workspace>`.

## W3b — The cockpit names the workspaces

- The cockpit's rail and dashboard list the workspaces above the tools; each opens Casefile on its first live
  application, and the dashboard counts what waits for the person per workspace. Casefile stays one tool (Akhil's
  decision of 2026-11-05: the instances are not separate products); the workspace is the level above it.
- `/workspaces`: each workspace with its members (editable by an administrator, with "open to everyone signed in"),
  its application instances (movable to another workspace with their data points; the address stays) and its data
  points with connector, place, rights and seed; the connectors below. Moves and member changes go to the audit log.
- In Casefile the word "workspace" is used for this alone (ADR-032 decision 9): what an application's setup page
  describes is the application.

## W3c — Own applications in workspaces

- Registry: an application `{"kind": "plugin", "plugin": "<id>"}`; its instance binds each of the plugin's `needs` to a
  data point, which may carry `mode`, `include` and `sensitivity` like a cockpit source. `own_instances()` reads them;
  `instances()` (Casefile, runner, pressroom-env) leaves them out.
- Cockpit: `config.add_own_instances()` turns each into a module with sources `<instance>.<need>`, through the same
  builder as a `[[module]]` of cockpit.toml (`config._module`: actions, read-only withholding, sensitivity). `/m/<id>` of
  such an instance opens for the workspace's members only; it is listed in its workspace (cockpit dashboard, Casefile's
  rail), not under Tools.
- "Tools" shows only plugins that live outside every workspace; with workspaces, no Casefile entry there.
- `retired` in plugin.json (schema extended): worklist, pipeline, gatehouse. A retired plugin still runs where
  cockpit.toml names it, but is refused in a workspace.

**Deviations from ADR-032**

- Data points on the server's directory connector keep absolute places where they had them; the connector carries no
  address per stage yet (decision 7 of the amendment). Each stage still has its own registry.
- Credentials do not live on the connector yet; today's connectors are file systems that need none. A mailbox remains a
  file in the tree (consequence 8).
- Rights are still enforced by the scoped store and the `/w/` gate, not through Nextcloud folder rights (SYS-150).
- Slots other than `cases` and `home` do not exist yet; the core still takes one root and one configuration (W5).
