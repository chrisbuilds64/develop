## Part 1 — Dependencies between cases

- `casefile/domain/depends.py`: references `CASE` or `<instance>:CASE`, kept in `meta.json` under `waitsFor`;
  resolution, release, the checks for existence, reach, self and circles.
- Step `wait_for` (`domain/step.py`): replaces the list, journaled, a thread entry; an empty list ends the waiting.
- The case view carries `waits` and `released` (`api/views.py`); API contract and types regenerated.
- Tests: `tests/test_depends.py`.

**Deviations from REQ-005**

- *Other instances* are reached through `targets.json` (ADR-022/023) until ADR-032's bindings exist. The resolver is
  one function (`depends.resolver_for`), so the switch touches nothing else.
- *Closed* means the case stands in a stage of group `out` or `archive` — the same groups the core already closes a
  case into. No new stage flag.
- *Released* is computed when the case is read, not stored and not announced in the thread.
- A circle running through a third instance is caught when that instance sets its own reference, not from here: a case
  reaches only the instances its own resolver reaches.
- The surface does not show `waits` yet; it arrives with the worklist's configuration (part 2).

## Part 2 — Configuration and demo world

- `config/worklist/`: stages Backlog, Next, Doing, Waiting, Done; every open stage offers a move to every other; whose
  move it is comes from the item's assignee; every member is an operator. Value lists: area (the cluster prefixes),
  priority, origin. Words in German and English.
- Core, for every application (Rule 17 — configuration, not a special case):
  - `field:<key>` as an actor (`domain/turn.py actor_of`): whose move is whoever the case's meta names there.
  - Declared fields (`domain/fields.py`, `theme.fields`): person, date, text or a value list; the step `set_fields`
    changes them, journaled, the thread names old → new; a new case may carry them.
  - `theme.create.slug: false`: the number alone is the case's name (`SYS-148`, not `SYS-148-title`).
- Demo world `build_worklist` (fictional), first in the public demo's list of worlds.
- Tests: `tests/test_worklist.py`.

**Deviations from REQ-005**

- *Creator* is the core's `created_by`; no second field.
- *Done sets the closing date* is the date of the move into Done, read from the thread; no `closed` field is written.
- An agent member cannot *reopen* a done item: the core reserves reopening to people (review S4). Agents move every
  open item.
- *Assignee* is checked against the instance's `people.json`, not a value list, so there is one list of people.
- Numbering counts within one data tree. Unique numbers across several data points of one instance follow in part 3.

## Part 3 — Data points with rights, share and delegate

- `casefile/store/multi.py`: `MultiStore` over a home tree and several `DataPoint`s (name, store, readers, writers,
  label). Per request it is scoped to the viewer: lists and finds only cases of readable data points, writes only into
  writable ones, starts a new case in the viewer's private data point. Numbers and uniqueness count over all of them
  (`everything`).
- `Settings.data_points` (casefile) and `data_points` on a workspace entry (cockpit registry, `workspaces.py`), passed
  through when the instance is mounted.
- Steps `share` (`to`: a data point; the case moves, its id stays) and `delegate` (`to`: a person; a new case with the
  next number opens in their private data point with origin, creator and link; mine closes with the reference).
- Cards carry `data_point` (the data point's label).
- Tests: `tests/test_data_points.py` (casefile), `test_a_workspace_carries_its_data_points_and_writes_them_back` (cockpit).

**Deviations from REQ-005 / ADR-032**

- *Rights enforced where the data lives*: on the server one process (the runner's user) reads every mount, so inside
  casefile the scoped store is the gate. Outside it, Nextcloud's folder rights are: each private data point is a team
  folder shared with its owner only. Both together are the protection; the surface filters nothing on its own.
- A data point is *private* when exactly one person reads and writes it; there is no separate flag.
- *Delegate* writes into a private data point the delegating person cannot read — the core's hand-off, journaled in
  the delegator's case. The delegator can no longer read the new case; the reference in their closed one remains.
- The registry keeps the old shape (one application per workspace); `data_points` is the first piece of ADR-032's
  format (SYS-150 continues it).
- Evidence names for PV-01/PV-02 are tests, not "operations": `test_every_person_starts_in_their_private_data_point_and_sees_only_what_they_may_read`,
  `test_a_case_of_an_unreadable_data_point_cannot_be_written`.

## Part 4 — Personal tokens

- `apps/cockpit/cockpit/tokens.py`: tokens `cbt_<id>_<secret>`, only the SHA-256 of the secret kept in
  `tokens.json` beside the accounts (600); owner, issuer, workspaces, read or write, expiry (1–365 days), revocation.
- The cockpit's identity takes `Authorization: Bearer cbt_…` as the token's owner; the gate before `/w/` lets a token
  reach only the API, only its workspaces, writes only with a write token, and the owner must be a member.
- CLI: `cockpit token issue <owner> --by <person> --workspace <id> [--write] [--days N]`, `token list`, `token revoke`.
  The owner issues for themselves, or the person an agent belongs to (`bill_to`) for that agent.
- Tests: `apps/cockpit/tests/test_tokens.py`.

**Deviations from REQ-005**

- *Issued on the account page* (O-4): issued on the command line for now; the account page follows when the surface
  work starts. Who may issue is the same rule either way.
- *Journaled with the token's owner* (IF-03): the owner is the identity the mounted application acts as, so every step
  is journaled under that name. The cockpit's own audit log does not record token use yet.
- Reachable from outside means through the cockpit's address (`cockpit.chrisbuilds64.com/w/<id>/api/…`), as F-10
  proposed; no new domain, no new port.

## Part 5 — todo.py as a client, and the move rehearsed

- casefile: `GET /api/export` — every readable case as data (stage, meta, closing date, change date, data point);
  `CASEFILE_DATA_POINTS` for a server started from the environment; `title` is a declared field of the worklist.
- `control/scripts/todo_remote.py` (private repository): with `worklist.json` beside `todo.json`, `todo.py` reads
  the cases through the export and sends every difference as a step (new item, move, fields, dependencies, reopen).
  The value lists stay those of the archived `todo.json`, read only. Without the server it reads and writes nothing.
- `control/scripts/worklist_migrate.py`: writes every item of `todo.json` as a case into the data points (Akhil's into
  his, the rest into Chris's), the instance's `people.json` into the home tree, and compares every case field by field
  with its source.
- Rehearsal, 2026-11-09, local casefile server on a copy: 370 of 370 items written, field comparison clean; Chris sees
  365, Akhil 5; `list`, `add` (with a dependency), `set`, `done`, `show` and a reopen through `set` all went through the
  server; `todo.json` unchanged.

**Deviations from REQ-005**

- *MV-02* (todo.py refuses to write todo.json): in client mode it never writes it; the hard refusal comes with the
  cut-over, when `worklist.json` is put in place and the file is archived.
- `done --date` cannot backdate: the closing date is the date of the move.
- New items get their number from the server, not from `todo.py`'s own count.
- Items assigned to Akhil are in his private data point and therefore no longer in Chris's list (MV-03 as decided);
  Chris sees them again once Akhil shares them.
